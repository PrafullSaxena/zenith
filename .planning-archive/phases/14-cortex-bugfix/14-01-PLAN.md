# Plan 14-01: Fix Parser Route Detection & CallEdge Wiring

## Goal
Fix two root causes that make BE repo APIs and Flows sections empty:
1. **CallEdge type mismatch**: Java/Python parsers define `CallEdge` as `{ from, to, type }` but the renderer and parser index expect `{ id, callerId, calleeId, filePath, line }`.
2. **CallEdges never collected**: Parser index (`index.ts`) pushes `entities` and `routes` from Java/Python results but **never pushes `callEdges`** into the `calls` array.
3. **Route path extraction bug**: The Java parser looks backward from the method declaration line for the annotation path, but the regex may fail for common Spring Boot patterns (e.g., annotation on the same line, multi-line annotations, or annotations without explicit path).

## Root Cause Analysis

### CallEdge Mismatch (Critical)
```
// java-parser.ts & python-parser.ts define:
interface CallEdge { from: string; to: string; type: 'inject' | 'call' }

// parser/index.ts, renderer, flow-utils ALL expect:
interface CallEdge { id: string; callerId: string; calleeId: string; filePath: string; line: number }
```

### Missing callEdges push (Critical)
```typescript
// parser/index.ts lines 155-160:
} else if (language === 'java') {
  const javaResult = parseJavaFiles(javaFiles)
  entities.push(...javaResult.entities)
  routes.push(...javaResult.routes)
  // ❌ Missing: calls.push(...javaResult.callEdges)
}
```

### Route regex (Medium)
The Java parser's route path extraction looks at lines `i-1` to `i-5` above the method, but the `@GetMapping("/path")` annotation might be on the same line as detected by the decorator scanner or might use different syntax.

## Tasks

<task id="1">
**Align Java parser CallEdge to canonical interface**

In `src/main/cortex/parser/java-parser.ts`:
- Change the local `CallEdge` interface from `{ from, to, type }` to match canonical:
  ```typescript
  interface CallEdge {
    id: string
    callerId: string
    calleeId: string
    filePath: string
    line: number
    type: 'inject' | 'call'
  }
  ```
- Update all places where callEdges are pushed to use the new field names (search for `callEdges.push`)
- Generate `id` as `${callerId}->${calleeId}`
- Use the caller's `filePath` and `line` for those fields
</task>

<task id="2">
**Align Python parser CallEdge to canonical interface**

In `src/main/cortex/parser/python-parser.ts`:
- Same changes as Task 1 — change `{ from, to, type }` to `{ id, callerId, calleeId, filePath, line, type }`
- Update all `callEdges.push(...)` calls to use the new field names
- Search for `from:` and `to:` in callEdge push calls and replace with `callerId:` and `calleeId:`
</task>

<task id="3">
**Wire Java/Python callEdges into parser index results**

In `src/main/cortex/parser/index.ts`:
- After line 159 (`routes.push(...javaResult.routes)`), add:
  ```typescript
  calls.push(...(javaResult.callEdges as CallEdge[]))
  ```
- After line 165 (`routes.push(...pyResult.routes)`), add:
  ```typescript
  calls.push(...(pyResult.callEdges as CallEdge[]))
  ```
</task>

<task id="4">
**Fix Java route path extraction regex**

In `src/main/cortex/parser/java-parser.ts`, the route detection at ~line 323-398:
- The current code looks backward from the method line for `@GetMapping("path")` but the decorator was already collected in the `decorators` array from scanning previous lines
- Fix: Instead of re-scanning backward, extract the path from the original annotation line that was already found during decorator collection
- Also handle: `@GetMapping` (no args = maps to ""), `@GetMapping("/path")`, `@GetMapping(value = "/path")`, `@GetMapping(path = "/path")`
- Handle multi-value: `@GetMapping({"/path1", "/path2"})` → create one route per path
</task>
